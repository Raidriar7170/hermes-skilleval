# 技术复盘（一页）

## 为什么 CI 会污染历史产物

release-check 默认把新报告写回 Phase17/18 的冻结目录。一次 CLI 测试就改写三份历史文件，后续一致性测试因同一污染连续失败；测试顺序因此影响结果。现在生成器默认使用新临时目录，显式历史输出先拒绝，CI 的报告进入 RUNNER_TEMP。历史 JSON、输入 hash、KEEP_BASELINE 与发布事实仍由原测试检查；当前首页改为测试可用命令和导航，不再要求永久保留旧阶段标题或 698 这一历史总数。否定句扫描按分句处理，肯定主张继续阻塞，歧义进入 REVIEW_REQUIRED。

## 为什么 fixture 拒绝不等于模型功能失败

源码、测试和普通 examples 数据有不同用途。仅按根目录一刀切会把合理数据新增挡在功能验证之前。未来任务使用显式 operations-v1，分别授权新增、修改、删除；examples 只允许有限类别和大小的非可执行数据新增。拒绝时保留候选补丁并标记未进入功能验证。旧 csvkit #1247 的两条 UNKNOWN、原规则和事后审计没有回写。

## 没有 gold 时能确认什么

可以确认真实执行发生、补丁相对哪个源码快照、重建是否一致、导入是否来自候选、相同预置检查在基线和候选上的差异。不能从 Agent 答复或“测试绿了”推出所有要求都已满足。已有检查与执行前定义的需求检查分开；候选自己改写的测试不成为认证标准。每项覆盖不足的要求保留 NOT_VERIFIED，整体 resolved 始终为空。两个不同任务的 N/F smoke 只证明入口工作，不形成修复率或成本优劣结论。

## 如何排除用户原有改动

基线取当前已跟踪文件的实际字节，包含暂存、未暂存修改及删除；显式包含的未跟踪文件另列。副本不共享原 .git 对象，Agent 内部 commit 不改变控制器的基准。补丁由基线与停止后的完整候选快照计算，再在第三个干净副本应用核对。原分支、索引、状态和选定内容前后比较；并发用户修改会被报告，控制器不会自动恢复或覆盖。

独立只读审查还发现并推动修复了 Git fsmonitor 宿主执行入口、preflight 超时容器清理和 NOT_STARTED 被误标完成的风险。首次真实启动在模型调用前被父目录技能检查拒绝，记录保留；修复隔离目录后继续同一请求。用户掌握程度未评估，本文不代签验收。
