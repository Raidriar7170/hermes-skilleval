# Hermes Goal：任务条件适用性数据与 Pointwise 支持学习

> 激活本文即开始实施；不是再次提交计划后等待批准。
> 本轮主线：**真实用途有差异的数据 → 合理的便宜基线 → 真正的逐样本监督训练 → 独立离线检查 → 条件满足时的少量真实验证**。
> 不继续用相同五项通用技能和一次新的 sigmoid 校准，代替适用性学习。
> 持续授权范围内必要操作，不逐阶段申请批准，不设置固定工程尝试次数；保留实际权限、已有费用授权和隔离边界。
> 这是新的限定研究协议，不回写旧实验，不保证正向效果，不把“全部回退但 CI 绿”称为有效支持模型。

---

## 0. 目标、核心问题与交付对象

本轮只回答：**给定公开维护需求、当前运行条件和技能原文，模型能否区分具体适用帮助、普遍适用的流程帮助，以及明确不适用的情况；这种区分是否优于固定方案和技能先验？**

最终交付三件东西：

1. 可追溯、按修复机制分组的适用性数据，能说明哪些差异值得学习；数据量与独立任务量分开。
2. 真实拟合、保存、重载并与便宜基线比较的 pointwise 支持模型，不再只有两参数分数映射。
3. 离线任务级选择结果、误差分析与可用推理入口；满足预先约定的支持条件时，接已有 runner 做小规模真实分支验证。

重要区别：

- **适用性**：技能原文提供的某个步骤，在当前需求和条件下适用。
- **任务特异性**：该步骤是否针对本需求的具体输入、接口、操作或约束，而不只是一般调试流程。
- **执行效用**：该技能是否真的改善 Agent 的补丁或成本；需要另有执行对照，不能由文本标签推出。

本轮主要学习前两者。不会将它们伪装成第三者，也不建设新的集合优化器、成本 Gate 或 Agent 框架。

## 5. 技能与任务目录：先证明自然差异存在

### 5.1 先定义研究范围，再看模型结果

从输入格式、公开接口、操作类型、数据保持要求、运行条件这些事实选任务，不按哪种策略会失败来选。

优先调查已有需求中的自然差异：导入/导出、CLI/API联动、schema变更、事务、类型/空值、增量或只读操作、格式与版本要求。这里只是调查维度，不是已经获得的新样本或伪造任务模板。

离线适用性任务需要公开请求、对应代码/文档版本、已知条件及来源；不必为每一条先跑完整 Agent。但进入真实执行子集之前，仍需使用既有 base/reference 资格与独立测试。

### 5.2 两套目录，各自完整报告

- `legacy-five`：保留原五技能与旧20任务，作为已观察诊断，不称新的独立检查。
- `task-conditioned-v1`：面向同一自然工作流，保留有用通用技能，并调查少量更具体的完整技能。

建议新目录约8–16项、约24–40个独立机制组作为资源起点，可能形成数百条任务—需求—技能记录。数量不是完成配额；不能把配对行数当独立需求数。

技能来源可为许可允许的既有公开包，或基于**修复前**贡献说明/公开操作流程整理的项目技能。后者标记为作者适配，不冒充外部独立技能。

禁止：只为制造负例添加医学/营销等无关技能；复制版本或拆碎原技能凑规模；将目标修复答案、未来提交、隐藏测试粘入技能；为新方法单独提供基线没有的资源。

索引可见不等于允许执行。完整包、资源、许可和依赖分别记录；仅有简介、缺关键脚本的对象不得混入可执行子集。

### 5.3 冻结目录与自然样本

先按内容和许可冻结目录。对预选自然任务尽量标注目录的全部技能，避免只给模型挑出的好/坏候选标注。

成本确实不允许全量时，冻结抽样规则并记录纳入概率；训练可挖难例，评估必须报告其候选覆盖与选择偏差。未知纳入概率的难例子集不能代表自然使用分布。

## 6. 标签协议：把“通用帮助”和“任务特定帮助”分开

采用新的 `conditional-applicability-v1` schema，保留旧标签字段及版本。不得静默将旧 SUPPORTED 改成新任务特定正例。

### 6.1 标签轴A：适用性

```text
APPLICABLE         有原文支撑的具体步骤，在当前需求/条件下适用
NOT_APPLICABLE     原文用途或明确前提与本需求不匹配
CONFLICT           已知操作/前提与请求或环境发生明确冲突
UNKNOWN            原文不足、关键条件未知、标注分歧或证据不完整
```

适用性不是“保证解决整题”。两个技能都适用是合法情况；不要求唯一正确ID。

### 6.2 标签轴B：特异性，只在A=APPLICABLE时使用

```text
TASK_SPECIFIC      帮助针对本需求明确的接口/格式/操作/约束
GENERAL_WORKFLOW   具体但普遍适用的调试、测试或完成前核验流程
UNKNOWN            无法可靠区分
```

不要按技能名称固定类别。一项通用技能的具体段落在某任务中也可能是 TASK_SPECIFIC；项目技能也可能对某任务只提供 GENERAL_WORKFLOW。

GENERAL_WORKFLOW在适用性上仍是正例，不是因“算法需要负例”而变成不适用。TASK_SPECIFIC也不是“实际效果必然更好”的标签。

### 6.3 辅助信息，不增加一堆分类头

保留角色 `procedure / implementation / verification`、应用步骤、条件、原文引用和不确定原因；角色可以多值。冲突优先来源于明确条件，不因未写依赖就判冲突。

本轮没有足够自然冲突例时，冲突分类质量标为未评估。少量人工构造的相反条件可以用于程序诊断，但不能拿来声称自然冲突召回。

### 6.4 需求粒度

优先把请求中的明确义务拆成少量原文可对应的需求，同时保留完整请求、否定与条件。拆分器不读修复/标签，不添加请求不可推导的新需求。

若请求无法无歧义拆分，保留 `composite_requirement=true`；不能把整题一个宽泛正例说成每项需求都获得覆盖。每个父任务的所有需求/改写必须在同一分区。

## 7. 标注过程：能自动做，但不能冒充人工真值

1. 两个独立上下文在不看预测分数、旧patch成败、参考修复的情况下作文本判断。
2. 每个判断包含任务/条件依据、技能原文引用、适用步骤和两轴标签；引用必须能在源版本逐字定位。
3. 程序验证来源和引用；语义判断不能仅由“字符串出现了”认证。
4. 分歧保持 UNKNOWN，可做独立仲裁并完整保留前两个判断；不反复问到得到所需标签。
5. 记录实际标注模型、提示词版本、请求ID/调用记录与成本；同模型不同会话只能称独立上下文，不称独立人类或独立模型家族。
6. 人工审核缺席不阻塞开发，但 `human_reviewed=false`，最终只能宣称对这套弱标签的拟合与泛化。

任务控制器为资格准备看到参考补丁，不代表标注子任务、特征抽取器或被测 Agent 可以看到。各自输入明确分离。

旧100行可以保留为已观察开发样本，也可按新 schema 重新标注；新标签另存，不覆盖旧文件。

## 8. 数据来源、难例与防泄漏

主数据必须来自实际任务和真实技能。三类数据分开：

| 类型 | 允许用途 | 不允许的声明 |
|---|---|---|
| 自然任务与完整目录组合 | 主训练、校准、检查 | 不等于真实用户流量 |
| fit内挖掘的难例 | 训练/开发 | 不代表自然类别比例 |
| 明确构造的条件变体 | 单元测试、挑战诊断或单列训练辅助 | 不是新的独立真实修复族 |

自然难例应来自真实差异：只支持另一格式、前提不具备、只读要求与写入操作冲突、只讲检查不提供所需转换等。不得捏造技能能力或删掉原技能里的限制。

同一技能在不同真实任务中有适用与不适用，才有条件学习的直接证据。若标签完全由skill_id决定，先说明数据缺乏这种信号，而不是把按技能记忆包装成任务理解。

不要通过隐藏公开修法或必要项目说明使任务更难；历史修复可能被底座预训练见过，只承诺本轮输入和划分受控。

## 9. 划分、统计单位与标签数据结构

### 9.1 分区

```text
fit       用于训练模型、先验、词表和简单特征
model-dev 用于选择模型配置/epoch/固定选择规则
cal       用于冻结模型后的概率映射与操作阈值
check     最终离线检查，不用于以上选择
```

按照修复机制、共同补丁家族和请求变体分组，不能逐行随机切分。原20任务均已观察，不再拿其原 final 名称宣称新盲测。

新 check 必须来自未用于本轮拟合/调参的机制组。允许同一个技能出现在训练和检查，这是已知目录、未见任务的研究；不能因此声称未见技能泛化。

如果规模不足四个分区，可以在开发范围内做按组嵌套交叉验证，并将整个结果降级为开发估计；不得把同一折同时当模型选择和独立确认。组级划分可参考 GroupKFold，但合并家族由任务来源决定。[E3]

### 9.2 字段最低要求

```text
row_id, task_id, requirement_id, parent_task_id, repair_group_id, split
repository, source_revision, request_ref, public_context_ref
skill_id, package_revision, package_hash, registry_id
applicability_label, specificity_label, roles, conditions
request_quote_refs, skill_quote_refs, application_explanation
label_source, annotator_ids, agreement, human_reviewed
origin_kind, derived_from, previously_observed
```

预测输入中不得包含 label、rationale、annotator、split、修复族ID、参考patch或隐藏测试。引用标注只用于检查可见性，不允许按正确答案引用位置为某个检查样本定制模型输入。

### 9.3 分母与权重

报告任务数、独立机制组数、需求数、技能数、配对行数和各轴已知/未知数。

主指标按机制组平均，组内先按任务平均、再按需求/技能行平均，避免一个任务因拆了更多需求占据全部权重。训练和基线使用同一事先声明的权重含义。

类别重采样仅用于fit，记录策略。自然check不为凑平衡重新抽样；挑战集单列。UNKNOWN不补成负例。

## 10. 数据可辨识性检查：先回答是不是只需技能先验

在fit与model-dev上产生一张实际数据表：每个技能的正负比例、通用/特定比例、涉及机制组、标注一致性、同一技能跨任务的标签变化。

必须回答：

- 存在多少真实的“同一技能，在条件A适用、条件B不适用”的组对？
- 存在多少任务让多个技能都适用，但具体帮助对象不同？
- 差异是否只是技能ID、模板句、标注者习惯或项目名称？
- 项目特定技能的正文是否偷偷包含某个修复答案？
- 阴性样本是否只来自一种格式/同一任务的很多变体？

不为通过这个阶段强制平衡标签。若所有自然技能几乎都适用，固定流程可能就是合理设计；做完已授权的相关目录调查后仍没有差异，交付明确的数据结论，不继续伪造“困难任务”。

若存在多个机制组上的自然两类信号，即使样本规模不大，也可执行声明为pilot的真实pointwise试验；不把任意某个行数当作统计充分性的保证。

## 11. 必须比较的基线

所有基线使用同一目录、请求、可见正文和公开上下文；输入截断差异单列，不偷偷给学习模型正确引用而不给基线。

| 基线 | 训练/使用方式 | 检验的问题 |
|---|---|---|
| Fixed workflow | 每个仓库/工作流在开发期固定两个技能，运行时不读任务 | 是否有必要动态选择 |
| Global prior | 仅由fit已知标签形成平滑常量 | 学习模型是否只是在预测总体正例比例 |
| Skill prior | fit中每技能平滑先验；未见技能回退全局 | 是否只是记住哪些技能普遍有用 |
| Cheap text model | 冻结fit词表的词法/稀疏交互特征＋正则logistic | 简单文本匹配是否足够 |
| Frozen scorer | 当前公开底座、相同输入协议，无新训练 | pointwise训练相对底座有什么增量 |
| Learned pointwise | 新adapter、相同文本与资源 | 能否学会任务条件适用性 |

固定技能只提供选择结果，不捏造概率来填Brier。概率指标比较适用概率模型；集合/Top-2指标比较选择方法。不可把不同对象硬塞进同一分母。

全局先验与技能先验的平滑强度在fit/model-dev确定。技能ID只允许在明确命名的先验基线使用；学习模型禁止读实验行ID/任务族ID，技能名称和正文作为自然输入保留。

增加一个开发负控制：只提供技能信息、不提供请求/上下文。如果其表现与新模型相近，应披露主要依赖技能先验，不能声称学会了仓库条件推理。

## 12. 真正的 Pointwise 训练

### 12.1 首选实现：共享底座、独立支持 adapter、两个任务指令

复用已合法缓存的 `pipizhao/SkillRouter-Reranker-0.6B` 底座；读取本机实际revision与库版本。原rank adapter冻结，不作为新支持adapter覆盖写回。

复用新版结构化输入和正确的最终yes/no评分，添加一个由程序控制的字段：

```text
judgment = applicability | specificity_given_applicable
```

- `applicability`：APPLICABLE为1，明确NOT_APPLICABLE/CONFLICT为0，UNKNOWN掩码。
- `specificity_given_applicable`：只在APPLICABLE且特异性已知时训练；TASK_SPECIFIC为1，GENERAL_WORKFLOW为0。

两个判断共享一份新支持adapter，使用不同的明确指令。这样GENERAL_WORKFLOW仍是适用性正例，只在特异性维度为0。

没有适用标签或特异性未知的行，不通过强行二元化补齐。冲突原因保持显式字段，不新增一个缺乏自然样本的“冲突识别专家”承诺。

### 12.2 训练目标

令各轴logit为z_a、z_s，掩码为m_a、m_s，组权重为w：

```text
L_app  = sum(w * m_a * BCEWithLogits(z_a, y_a)) / sum(w * m_a)
L_spec = sum(w * m_s * BCEWithLogits(z_s, y_s)) / sum(w * m_s)
L      = L_app + lambda_spec * L_spec
```

分母为0时该轴不训练、状态明确，不产生NaN。lambda_spec仅在model-dev选择。优先不加pairwise项，先检验逐样本监督本身；不能仍只训练分差，却将绝对输出称已学会支持。

使用数值稳定的logit损失，正确处理掩码、类别权重和批次维度；PyTorch的BCEWithLogitsLoss可用于这一实现。[E4]

### 12.3 模型配置与实际验证

建议从LoRA r=8、已观察到的q/v投影、低学习率和小batch开始；这是初始配置建议，不是固定尝试配额。不得搜索一堆更大backbone规避当前数据问题。

输入预算根据实际显存和关键证据长度确定；先保证指令、请求条件和需要判断的技能内容确实可见。不能为了省内存把8192直接压回1024，却不报告关键证据丢失。

资源不足时可减少batch、使用已有环境支持的梯度累积或确定性证据压缩；压缩只依据公开请求，不使用check引用标签。必要时分片，必须保留条件与否定。

必须保存：真实训练配置、模型/数据身份、掩码分母、有效梯度、参数变化、逐epoch开发结果、训练耗时、设备与峰值内存。不要将loss下降等同样本外能力提升。

checkpoint在新进程重载，验证两轴输出与保存前一致；若增加分类头，需连同adapter一起保存，不允许只保存LoRA而丢失训练头。[E5]

至少与同输入的冻结底座比较。数据条件成立时，不能只完成数据与校准脚本而把pointwise训练再次留给下一轮。

## 13. 校准和检查集常量口径修正

### 13.1 明确数据职责

fit/model-dev选择并冻结scorer以后，才在cal上拟合低自由度映射。check不参与训练、模型选择、阈值选择、标签争议裁决或资源配置。

两轴的校准意义不同：第二轴是已知适用条件下的特异性判断。cal中没有足够的适用/特异性标签时，该轴保持未校准，不把它当完整概率使用。

Brier/log-loss同时受区分能力和校准影响，不用一个数声称“完全校准”；报告可靠性分桶和覆盖。[E1]

### 13.2 修正基线而不改历史

新报告必须同时区分：

- `frozen_global_prior_brier`：fit阶段得到的常量q，冻结后在check计算误差。
- `frozen_skill_prior_brier`：仅由fit形成的每技能先验。
- `posthoc_check_prevalence_reference`：如保留check自身比例p*(1-p)，明确是事后参考，不能叫可部署基线。

旧0.174375字段不原地覆盖；可以在新说明解释其含义。DummyClassifier的prior来自fit数据，可用作实现核对参考。[E2]

### 13.3 操作点不等于研究是否执行

完整离线排序/区分能力比较必须进行，不能因为没有0.90操作点，就取消所有离线结果只跑回退smoke。

高精度受支持分支默认沿用0.90作为新的暂定接受目标，并配合预先写明的非零覆盖/机制组条件；该数不是行业标准。具体条件在本轮cal预测之前冻结，不能根据0.8875的旧结果降到0.88。

报告完整precision—coverage曲线、接受样本数、机制组数、UNKNOWN接受数与不确定性，不只报告最佳点。零接受时precision=null，不能报告100%精度。

如果需要新的风险容忍度，它必须在新结果出现前作为独立研究模式定义，不能事后替换主模式。没有合格点时保留rank-only advisory离线比较，但它不是“有效高精度支持分支”。

## 14. 选择评估：适用和优先两个问题分别比较

保持K=2，不引入新集合算法。

第一张表：适用性分类与拒绝，包括正负区分、冲突/不适用误收、UNKNOWN、校准与覆盖。

第二张表：任务条件排序，包括任务特异帮助Precision@2/Recall@2、多正例平均排名与已知不适用率。没有任务特异正例的任务单独列出，不悄悄从全任务表删除。

可预先定义排序分数为：

```text
specific_priority = p_app * p_specific_given_applicable
```

它是文本优先级代理，不是预期修复收益；两轴未充分校准时只能称排序分。所有技能仍须通过明确环境/文件约束。

通用技能不能仅因specific_priority低就被描述为有害；Fixed与Skill-prior必须留在对照中。任何按文本特异性排序的改进，都还不能推出实际任务效果更好。

第三张表：有限操作点下的Top-2集合，记录能否选满、实际支持依据与回退。未达两个合法候选时不得凑数；不要只对非空样本计算全局成功率。

固定原rank的同K实验与新priority实验分开：前者只检验支持过滤增量，后者检验新文本优先级，不能混在一条“全部提升来自校准”的结论中。

## 15. 主指标、消融与失效解释

至少输出以下三组指标，不以测试数为成果主指标：

| 层次 | 指标 | 必要限制 |
|---|---|---|
| 数据 | 各轴已知/未知、分歧、任务/机制/技能量、条件反转 | 行数不是独立样本数 |
| 离线模型 | 按族Brier/log-loss、AUPRC/AUC、按技能结果、任务特异Top-2、误收/拒绝 | 类别比例与单类分区必须披露 |
| 条件执行 | 实际选择/物化/读取、目标+回归、耗时和真实用量 | 文本精度不等于修复收益 |

AUC只在同时有两类的对象上计算；按技能宏平均报告覆盖了哪些技能，不能把单类项填成1。高正例比例下，不用accuracy隐藏已知负例全部判错。

执行必要而小的消融：冻结底座vs新pointwise；新模型有/无同一公开上下文；有/无特异性辅助任务。去上下文的推理消融不冒充另一个独立训练模型。

至少走读以下错误：通用技能被误判为任务特定；格式/输入/版本前提忽略；否定/保留要求误解；仅凭skill name判断；模型只复制先验；两个标注者同样偏误。

置信范围按任务机制组重采样，行内相关不能当独立样本。样本小就标探索性；不以差异不显著宣称等价、非劣或安全。

## 16. 条件式少量真实验证

只有在冻结cal规则后，check出现有原文依据的非空受支持选择、且没有明显资格/标签矛盾时，才自动进入真实执行验证。

执行子集应在看到相应模型分数/patch结果前预选，优先从已有合格工作流与未用于调参的任务中选取；不挑模型最容易赢的题。离线check若触发是否继续的全局决定，后续运行称条件性机制验证，不夸大成独立大型效用实验。

使用同一上下文、同一目录、同一Agent/预算、同一技能呈现：

```text
N+：原生渐进选择
B2：冻结排序器的两个候选
C2：同排序器、同K，使用新支持通道作资格/选择
```

Fixed已经在离线主表中；若执行子集要加F，需事先写入方案，而不是看到C2失败后临时替换基线。

建议从少量独立机制任务开始，不是再跑48次以上完整五臂矩阵。两到几项任务可验证实现机制，但不支持总体成功率提升。

真实要求：候选经现有完整包物化；记录实际暴露、可观测读取、fallback、完整patch、干净重建、目标与回归。少于两个合法候选的C2保留回退，不能统计为同K成功。

如果cal/check没有有效操作点，停止这一执行扩展并保留NOT_EXECUTED原因；无需再跑一次全回退smoke证明同一个入口。离线学习结果仍应完整交付。

## 17. 成本、资源与续跑

先估算三类不同开销：公开资料准备/标注、训练/离线评分、可选Agent执行。Goal界面总token不是算法在线token，也不是付费金额。

不设置固定工程尝试次数；有限实验规模、每请求timeout、磁盘和显存保护不是retry上限。
