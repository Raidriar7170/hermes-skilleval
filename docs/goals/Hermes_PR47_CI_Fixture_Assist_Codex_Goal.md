# Hermes Goal：修复 CI 阻塞、对齐文件策略、交付最小 assist

> 激活本文即继续开发，不停在计划或等待批准。
> 在现有 PR #47 上完成一轮可用性收束：**可靠 CI → 合理的未来任务文件策略 → 当前任务 assist → GitHub 可审阅交付**。
> 不扩大 benchmark，不重训，不开发第三版选择器；旧实验与两条 UNKNOWN 不改写。
> 本轮 `assist` 是核心交付，不能再次按上一轮的可选项延期后宣称完整完成。
> 持续授权范围内必要操作，不重复申请阶段批准，不设置固定工程尝试次数；实际系统权限、资源预算与任务隔离仍然有效。

## 0. 本轮目标与完成后的使用体验

把当前“能够回放已经准备好的历史任务”的入口，推进到：

```text
用户给出受支持仓库的本地副本、当前需求与允许的检查
    → preflight 列出输入、权限、文件策略和缺少的资源
    → 创建独立源码快照，不修改用户原工作区
    → 使用 native 或 fixed 调用现有 Agent 执行器
    → 捕获新增、修改、删除形成的实际补丁
    → 在新的候选副本应用补丁并运行约定检查
    → 给出补丁、检查结果、未验证要求与真实开销
```

与此同时，项目自身测试和 release/CI 检查能够在干净 checkout 上运行，不写坏历史产物，不因旧 README 字符串或否定句误报持续阻塞。

本轮交付必须有三部分：

1. **CI 修复：** 定位真实根因，修复当前合并阻塞；不是只证明“与坏基线一样”。
2. **文件策略：** 为新任务允许正常测试数据位置，严格区分允许操作、策略拒绝与功能失败。
3. **最小 assist：** 无参考补丁、无历史 qualification 也能实际执行，交付可验证补丁与有限检查结果。

已有原生/固定/强检索路径继续保留。默认原生，固定技能显式可选，强检索保持可选；本轮不晋升路由模型，也不改变旧 N/F/S 研究结论。

**本轮不是效果研究。** 不承诺提升成功率、节省 token 或证明生产采用。一次当前任务 smoke 只证明该入口实际工作，不作为新的统计修复率。

## 2. 持续授权、执行与发布范围

### 2.1 激活即授权的操作

持续授权读取项目和相关公共资料，在本轮隔离工作区修改源码、测试、文档、必要配置；安装用户态隔离依赖；使用已授权的模型、登录和个人计算资源；运行测试、构建 wheel、执行真实 assist smoke、修复普通失败、重算记录、本地提交及指定分支推送。

### 2.3 明确不做

- 不购买、充值或新订阅服务；不调用未获费用授权的 API，不从旧 SSH 配置推定公司机器仍可访问。

## 4. 执行顺序与阶段交付

| 阶段 | 主要工作 | 必须出现的结果 |
|---|---|---|
| C1 | CI 根因与小范围修复 | 当前门禁不再因已知维护缺陷失败，历史产物不受污染 |
| C2 | 新文件策略与旧规则兼容 | 合理 fixture 允许，危险/越界修改明确拒绝，旧记录不变 |
| A1 | assist 编排与副本/补丁闭环 | 不依赖 gold/qualification，实际修改发生在独立副本 |
| A2 | 检查结果与使用性 | 区分已有测试、新检查、未验证要求；干净 wheel 可运行 |
| A3 | 真实 smoke 与负向测试 | 实际 Agent、真实补丁、干净重建、原工作区不变 |
| G1 | GitHub 最终交付 | 精确 HEAD 的 CI、可读代码/证据、更新 PR 和审阅入口 |

CI 与 assist 可以在不共享可变状态的情况下并行准备，但必须分别验证。即使发现一个 CI 问题需要进一步定位，也应完成不受影响的 assist 工作；不能用一个子项的外部阻塞掩盖其他项尚未开始。

## 5. C1：修复当前测试与历史记录的耦合

### 5.1 先建立简短的失败映射

每一组失败记录：失败测试/检查、复现命令、根因、实际修复、需要保留的行为。相同根因可以合并，不能因“与基线签名相同”直接忽略。

保留必要的 before/after 日志。不要反复全量跑25次，也不要将每个失败变成新审批阶段。

### 5.2 当前 README 与历史事实分开测试

- 当前 README 验证：安装、使用、支持范围、结果/历史导航是否存在且链接有效；中英文入口各自检查。
- 历史阶段事实：检查相应冻结文件或明确历史快照，不要求当前首页永久包含旧标题、勾选框或698这一旧总数。
- 测试数量如果展示，说明对应版本/范围并从运行结果获得；不把动态总数硬编码成永远不变的文案。
- 更新测试前写明它原本保护的语义，用等价或更清楚的断言继续覆盖。
- 不通过在 README 塞入过时、误导性句子满足老断言，也不删除历史事实测试来省事。

### 5.3 生成测试使用临时目录，历史证据只读

测试中的 phase17/phase18 生成、release-check、manifest 和 summary 必须输出到 `tmp_path` 或本轮专用运行目录；不得指向受保护历史目录。[P1]

区分三个测试对象：

1. **历史记录一致性：** 按原绑定版本和原输入校验冻结记录。当前 README 不应被冒充历史输入。
2. **生成器的现在行为：** 在临时夹具中验证 PASS、FAIL、REVIEW_REQUIRED、缺证据等真实分支。
3. **当前仓库的就绪检查：** 针对本次代码与文档生成新的报告，不覆盖旧 release manifest。

如当前历史文件本身不是 PASS，就如实测试其状态和来源；不能改成 PASS。若历史输入和文件不一致，需要查明原绑定/快照，给出旁置更正说明，不能直接改历史摘要凑一致。

默认 CLI 仍可能需要支持历史用法。对输出默认位置的必要迁移要给明确的新位置或友好错误与文档；不能 silent no-op 后返回成功。显式要求写冻结目录时应保护原数据，不通过 `git checkout` 把测试污染事后擦掉假装没有发生。

新增一项回归：运行相关生成/检查后，受保护目录字节及 Git 状态不变；按不同测试顺序运行关键组合不再引发后续失败。完整测试后也检查保护范围。

### 5.4 修复 overclaim 否定句误报，但不绕过检测

最小回归集覆盖：

| 示例 | 预期语义 |
|---|---|
| “这不是公开标准 benchmark、排行榜或 SOTA 证据。” | 否定，不应仅因出现 SOTA 被认定夸大 |
| “This does not establish SOTA.” | 明确否定 |
| “本项目已经达到 SOTA。” | 肯定主张，需要证据或按现有规则标记 |
| “这不是玩具项目，已经超过所有 SOTA 系统。” | 后一分句仍是肯定，不得被前面的“不是”豁免 |
| 引用、反问、混合否定、无法可靠判断的句子 | 清楚的歧义结果/诊断，不能全当肯定或全放行 |

只修当前扫描器的可解释、确定性边界；不引入新的 LLM 审判服务。不使用按README路径全局跳过、删除整个检测、把任何含not的段落都白名单化等捷径。

如果保留局部例外，必须窄到具体有语义依据的情形，并用肯定反例验证不会漏放。歧义输出沿用现有 review/warning 机制，不能偷偷变成高置信度 PASS。

### 5.5 当前 release/CI 应验证真实结果

- 失败步骤即使采用 `continue-on-error` 以收集日志，最终汇总仍必须读取真实 outcome。
- 不以 `|| true`、缩小 pytest 范围、排除整个历史目录、宽泛 skip/xfail 或替换失败码制造绿灯。
- 合法调整历史快照测试不是禁区；必须保留其原保护目标并说明迁移关系。
- 若某项“未批准发布/未晋升模型”是合法历史事实，将其与“当前生成器工作正常”区别处理；不能把不晋升模型自动改成晋升。
- 拆分当前产品检查与历史记录检查后，两者都应实际运行，不是把红项移到无人运行的角落。
- 现有 OpenSpec、集成、Ruff/mypy 非回归要求维持；不为了本轮大规模清理所有无关类型债务。

## 6. C2：为未来任务对齐正常文件操作

### 6.1 旧协议不变，新策略明确版本

保留旧 csvkit profile、#1247 的两份原补丁、UNKNOWN、原拒绝原因与 post-hoc 审计，不把新规则应用后结果回写旧主表。

创建或扩展用于 **未来 replay/assist** 的策略版本。旧 task.json 不含新字段时走原语义；现有记录重算仍生成同样的历史数值。使用显式版本或兼容解析，不默认给所有旧任务放开新路径。

### 6.2 规则按路径和操作定义，不只是一个根目录名单

最小能力：

- 已允许源码/测试目录的修改，继续按声明处理。
- 为确有该惯例的 csvkit 开发场景，允许受限的 `examples/` 测试数据新增；如果任务确需修改已有例子，必须由本次预置策略允许，不能由 Agent 自行决定扩权。
- 文档修改按指定路径明确允许或拒绝；不要因为文件在仓库里就全部允许。
- 控制器持有的可信测试、评价配置、运行环境依赖锁、验证器执行入口和凭据继续受保护；这不等于禁止修改任务仓库本来需要修复的CLI源码。
- 能区分新增/修改/删除；重命名视为删除与新增的组合分别验证。不存在相应操作授权时明确拒绝。

为测试数据选择合理、有限的文件类别和大小保护。不能把 `.py`、shell、配置文件当普通数据一概放行；也不要仅凭扩展名宣称内容安全。资产仍只在隔离环境使用。

在 prompt 和 preflight 中明确写入同一份实际策略。提示词不能声称允许、捕获器却拒绝，也不能提示受限而实际无限制。

### 6.3 路径检查与捕获必须一致

规范化相对路径并拒绝绝对路径、`..` 越界、符号链接逃逸、特殊文件、异常补丁头与含糊路径。大小写/平台差异要说明支持范围。不要使用字符串前缀导致 `tests_evil/` 被当 `tests/`。

删除、未跟踪新文件、Agent 已提交的修改仍由控制器对基准快照计算；不相信 Agent 自己报告的 diff。

策略拒绝时保留完整候选补丁与理由，标记“未进入功能验证”。不能自动删除违规文件后把剪裁版标成原补丁通过；如做修正，是新候选，保留父记录。

### 6.4 最小测试

正例包括正常新增CSV/JSON测试数据和允许目录内的回归测试；负例包括改可信检查、穿越/符号链接、伪装可执行文件、删除不允许的原fixture、超限文件。

用同一不敏感fixture验证 prompt 披露、preflight、捕获和最终验证的一致性。允许使用微型合成文件测试策略本身，但不能把它们包装成真实修复研究。

## 7. A1：最小 assist 的接口合同

本轮优先支持已有 sqlite-utils/csvkit profile 的本地副本。未支持布局应在调用模型前报错，不自动声称任意 Python 项目都可运行。

建议入口如下，**这是待实现的接口示意，不是假称现有CLI支持这些参数**：

```sh
hermes-maintain assist \
  --repo /absolute/path/to/local-repository \
  --request /absolute/path/to/public-request.md \
  --repository-config /absolute/path/to/repository-config.json \
  --checks /absolute/path/to/allowed-checks.json \
  --registry /absolute/path/to/skills/registry.json \
  --skill-assets /absolute/path/to/skills \
  --arm N \
  --output /absolute/path/outside-repository/new-run
```

实际命名可沿用项目风格，最终以可运行help、安装后测试和文档为准。必须具备：

- 明确仓库、需求、profile、检查、技能来源和输出位置。
- N 为默认；F需要合法固定配置；S可继续使用现有可选模型配置，不要求本轮重跑S研究。
- N/F 不加载检索用 Torch/Transformers 或下载检索权重；它们仍然需要真实执行 Agent 的授权登录，不能声称“不用任何模型”。
- `preflight/plan-only`（名称可调整）能够只检查配置并显示副本范围与缺失项，不调用模型、不修改原仓库。
- CLI 和结构化输出给出可执行错误，返回码与检查结果一致，不依赖控制器隐藏的 Notebook 状态。

**assist 不接受也不要求 reference patch、历史 gold、旧任务 qualification 或伪造 oracle。** 复用执行步骤，不复用“只有知道答案才允许运行”的前置条件。

## 8. assist 的输入快照与原工作区保护

### 8.1 当前状态是基线，不默认等同于 HEAD

用户可能有已暂存、未暂存和未提交文件。对明确包含在范围内的当前文件取一致快照，记录当前内容；新补丁必须相对此快照产生，不能把用户已有修改算成 Agent 新贡献。

默认收集受支持的已跟踪源码/文档/测试；新未跟踪文件仅按显式输入/包含规则加入。忽略项、模型、虚拟环境、构建输出、`.git`、凭据和运行日志不自动进入模型上下文。

若检测到会影响任务的排除文件、敏感内容或不支持的链接结构，给出明确 preflight 状态，不悄悄用不完整副本冒充完整仓库。公开 smoke 选无敏感内容的合法副本，避免把用户私有目录用于演示。

### 8.2 执行与导出

- 输出目录位于输入仓库外；新 run 使用新目录，禁止递归收集自己的输出。
- 在独立副本中运行，原工作区不挂载为可写。
- 拷贝必要源码而非共享含未来历史的 Git 对象；副本需要 Git 时由控制器建立独立基线。
- 原仓库的branch、index、tracked与相关untracked内容在执行前后保持不变。真实用户同时编辑时报告外部变化，不能覆盖或自动恢复用户的新内容。
- 以基准快照和结束后的完整允许文件集合计算 patch，捕获新增/修改/删除；不依赖 Agent 的commit、最后答复或自报diff。
- 在另一个干净快照重建候选，验证重建内容与捕获内容一致，再运行检查。
- 超时、异常、取消时先停止本次进程组/容器，确认不再写文件，再捕获可用补丁。不能边运行边认证最终状态。

本轮不实现自动应用到原仓库、自动提交到用户业务分支或自动push业务仓库。输出补丁及人工可用命令即可。

用户以后明确提供私有仓库运行assist，不等于允许将其代码或产物公开到GitHub；本轮公开smoke只用合法公开开发副本。

## 9. A2：无参考修复时，怎样报告验证

### 9.1 把三类检查分开

| 检查来源 | 用途 | 不能推出什么 |
|---|---|---|
| 输入快照中既有检查，由控制器保护执行方式 | 判断已覆盖行为是否退化 | 不能证明所有新需求被满足 |
| 执行前从明确需求定义的额外检查 | 验证具体可执行要求，保留来源与适用范围 | 不能叫上游隐藏gold或无遗漏规范 |
| Agent新增或修改的测试 | 提供额外开发信息 | 不能由候选自己修改标准后给自己认证 |

检查定义从已指定的控制器配置读取，执行开始后不让候选改写。用参数数组执行允许命令，工作目录、环境和超时显式配置；不要把外部仓库提供的任意字符串直接在宿主shell执行。

复用现有隔离、候选包来源检查与可信加载器。先确认导入的是重建候选，而非系统已安装修复版；测试要求写临时文件时给独立临时区，不给原工作区或可信检查目录写权限。

对于无法纳入可信加载路径的项目测试，准确标“候选环境自测/较弱隔离”，不要继承隐藏测试的强结论。

### 9.2 基线检查与候选检查成对记录

在源快照及重建候选执行相同约定检查。原仓库本来失败时记录 pre-existing failure，不能把它归为候选新增问题；也不能把候选出现新失败隐藏在“基线本来红”中。

测试收集为空、必需测试skip/error、执行超时、候选导入错误要单列。不是简单看到exit 0就判定所有要求验证。

用户需求若明确改变旧行为，控制器可在执行前声明相应检查调整；不能在看到候选失败后静默修改预期。修正规范需形成新记录并解释。

### 9.3 结果不制造“全部解决”结论

最小结果包含：

```text
工程执行状态：完成 / 部分完成 / 失败 / 取消
补丁：路径、基线身份、变更摘要、重建结果
文件策略：接受 / 拒绝及原因
既有检查：基线与候选结果、新增失败、未知项
需求检查：每项明确要求的可执行验证或 NOT_VERIFIED
成本：已观测的执行/验证/选择耗时与用量、未知项
```

没有充分外部判据时，整体任务是否解决保持未知，不沿用历史 replay 的 `resolved=true`。可以明确报告“已有检查全部通过”，但不写“用户要求已经全部满足”。Agent文字解释不构成独立判据。

缺需求检查时列出缺口而不是生成一个肯定评价填上。允许报告没有产出补丁或任务本来无需修改；但核心 smoke 必须实际验证非空补丁路径，不能只交付no-op演示。

## 10. 复用执行器，不复制第三套框架

将 `_maintenance/execute.py` 必要逻辑提取成可调用函数，薄CLI分别提供 replay 与 assist 的任务合同。

共享：技能解析/物化、模型传输、会话隔离、进程退出、补丁捕获、干净重建、候选导入核查、用量和清理。

不同：

- replay 要求资格记录、固定base/目标/回归与参考修复来源。
- assist 要求当前快照、明确文件策略与允许检查，不要求gold，不输出同等级的修复认证。

不要把 replay 的安全检查整体删除以让 assist 运行；也不要给 assist 填一个假的qualified=true绕过前置条件。

保持当前 replay CLI 和 records-only 行为兼容。旧 N/F/S 数据重算前后数值一致，不要求重跑旧模型实验。

配置实际生效：请求、路径、策略、超时、模型、effort、检查与输出都有真实连接。无法支持的字段启动前拒绝，不把传入JSON原样复制成“有效配置”。

模型/effort先用当前已有权限与本机实际能力核对，不为了新版本名称替换历史记录。新 smoke 如使用不同模型，单独说明，不与旧成绩直接比较。

## 11. 成本、失败恢复与清理

使用统一的单调时钟记录 preflight、快照、技能准备、可选检索、Agent、捕获、重建、验证和整个请求wall time。嵌套区间不能重复相加；累计worker秒和用户等待秒分开。

记录真实可得的输入/输出/缓存用量；缓存输入和推理输出分别是相应总量子集。无终止事件的用量为未知，不填0。美元费用没有实际依据时保持未知。

缺模型登录、Docker、profile依赖时尽量在 Agent 调用前给出可操作的错误。允许任务输出部分补丁，但不能把未运行检查说成通过。

断线或重试先判断原进程是否仍在执行。恢复使用本次run身份，不盲目重复启动昂贵任务。普通基础设施问题可以修复重跑，保留所有真实执行，不择优、不掩盖失败。

只停止本次创建的容器与进程，不使用全局docker prune或杀掉所有Python/Codex。凭据由既有传输边界处理，不能进入候选可读范围、公共日志、异常栈或仓库文件。

## 12. 最小验证矩阵：重点是功能，不是数量

### 12.1 无模型自动测试

至少覆盖以下行为，优先复用现有测试fixture：

- CI文案检查语义仍受保护，肯定夸大不被否定规则漏放。
- release/测试输出不污染历史目录，依赖测试顺序不再改变结果。
- 新旧策略版本并存；正常新增fixture允许；危险/越界/未授权删除拒绝。
- assist无需gold/qualification，replay仍要求原前置条件。
- 当前脏工作区取快照、补丁只包含新变化，源仓库不变。
- 新增、删除、Agent内部commit、未跟踪文件和失败中间产物正确处理。
- 没有参考或检查时不能输出完整解决；空收集/skip/超时/导入错误不误判通过。
- 候选修改自己的测试不能覆盖控制器检查；既有失败与新增失败区分。
- CLI参数、相对路径、含空格路径和错误配置在安装后仍正常。
- native/fixed与records-only不导入检索依赖或触发下载。

单元测试可以mock外部服务，必须明确是单元测试；真实assist验收不能由mock替代。

### 12.2 实际当前任务 smoke

在已有两个支持仓库的合法开发副本中分别走通一次实际assist路径：至少覆盖一次N、一次F，使用真实已授权Agent和实际非空代码修改。

任务可以来自当前可复现维护需求，或先明确记录的合理开发请求；不是把已准备好的历史任务连同参考修复输入后改名assist。至少一个案例不是之前冻结六个修复族的再次回放。

选择请求时优先已有依赖可运行的小范围真实维护问题；不需要为了验证入口另外搜几十道题。自行提出的开发请求明确标 `developer-defined smoke`，不说成外部用户需求。

每次保存：源快照、公开请求、允许检查、实际包、事件用量、补丁、重建、检查范围及原工作区不变证据。新加文件策略至少在一个真实或针对性集成案例中覆盖正常fixture，而不是只验证提示词。

工程成功条件是入口能真实编排并如实处理结果；不要求所有任务由Agent完美修好。不过至少要有一个实际非空补丁通过约定的合理检查，才能证明正向闭环，而不只是演示错误提示。没有做到就标部分完成，不追逐“两个案例都必须成功”的结果。

两次smoke不是新增N/F对照研究；不同任务、不同臂的结果不能组成胜率比较。S路径不要求重新跑完整任务，只做必要兼容检查；无本轮新S推理就不要新增其效果声明。

### 12.3 干净安装与CI

构建wheel，在仓库外的新环境安装，不设置指向checkout的PYTHONPATH，不用editable install代替打包验收。

检查help、doctor、preflight、N/F推荐、records，以及实际assist需要的模块/资源。N/F控制器环境不安装Torch/Transformers/sentence-transformers仍应可启动；真实执行Agent在其已配置环境调用。

wheel中的配置/资源必须可定位，不能从当前工作目录暗中读取仓库内脚本。已声明需用户提供的资产给出实际准备步骤。

完成聚焦测试后运行完整轻量套件与既有门禁。耗费模型额度的smoke不默认在每次公开PR CI自动触发；CI用无模型集成测试及已有记录验证软件行为。

## 13. 提供实际可用的最短说明

使用入口以一个不看历史聊天的开发者为对象，文档应清楚包含：

1. 怎样安装，哪些部分需要Docker/登录，哪些不需要检索权重。
2. 怎样配置受支持仓库、请求、文件策略、检查和技能。
3. 一条经过实际测试的preflight与assist命令。
4. 去哪里看补丁，怎样在自己的副本中检查/应用；不会自动修改原仓库。
5. replay与assist的验证差别、未知要求和失败状态。

不新建前端。默认控制台摘要+Markdown/JSON报告即可。演示只针对确实支持的仓库与环境，不写“任意repo一键修复”。

更新README中的当前功能入口，链接历史研究而非把所有阶段写回首页。保留局限说明但不要让首页变成几百行状态台账。

**避免提交身份循环：** 最终代码/文档提交后运行对应CI，再用PR正文/评论记录该HEAD结果；不要每次为了把新HEAD写入文件又产生另一个HEAD，然后无限追逐同一验证。旧实验源码、当前交付源码与当前CI源码分别标识即可。

## 17. 完成条件与停止状态

| 项目 | 完整完成所需证据 |
|---|---|
| CI | 当前完整轻量测试/必要门禁实际通过；精确head的GitHub结论可读取，旧产物未被测试污染 |
| 文件策略 | 新策略允许正常fixtures且拒绝越界，旧配置仍按原规则解释，提示与执行一致 |
| assist | 无gold/qualification的真实执行、非空补丁、干净重建与有限验证，不修改源仓库 |
| 安装 | 仓库外wheel、N/F无检索依赖、实际帮助/命令/资源路径正常 |
| 历史兼容 | 旧records-only数值不变，旧replay前置条件和可信检查未被assist削弱 |
| GitHub | 同一Draft PR包含可审阅源码、最小证据、使用入口及实际新HEAD |
| 结论 | 不把软件功能通过说成算法增益、完整解决或生产采用 |

分别报告下列维度即可，不要创建复杂的新状态体系：

```text
engineering: COMPLETE | PARTIAL
ci: PASS | FAIL | PENDING
assist: IMPLEMENTED_AND_SMOKE_TESTED | IMPLEMENTED_UNVERIFIED | NOT_IMPLEMENTED
publication: PUSHED_DRAFT_PR | PENDING
historical_research: UNCHANGED_INCONCLUSIVE
```

整体完整完成要求核心工程、真实smoke和最终CI已验证。不接受“assist以后再说”却标完整完成；本轮已将它提升为核心要求。任务Agent未完全满足某个需求但正确报告了未知，可以保留为功能案例，不把未知伪造为通过。

新算法收益不是完成条件；也不要求修好所有任务、运行完整S矩阵或取得人工答题确认。

若真实权限、模型额度、Docker或远端CI不可用，完成其他可完成内容并交付具体阻塞和恢复命令。不得降低标准伪造完成，也不反复索要授权。

完成后停止，不自动开新仓库研究、默认路由晋升或部署。

## 18. 给用户与后续审阅的交付

最终回复保持实用，依次给出：

- PR链接、分支、完整head和该head的CI链接/真实结论。
- 三类CI问题怎样修，是否还存在阻塞；本地与远程测试分别多少，不冒充独立重跑。
- 新策略与历史记录关系，旧UNKNOWN仍保留。
- 实际assist支持范围、真实smoke、补丁与检查结果，以及哪些要求仍未知。
- 一条真实安装后的运行命令和先读文档。
