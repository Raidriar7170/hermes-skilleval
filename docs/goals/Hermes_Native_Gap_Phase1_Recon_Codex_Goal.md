# Hermes 第一阶段：原生能力、真实数据与可执行场景探查

> **Codex Goal｜先确认研究起点成立，不开发新的技能路由算法。**
> 编制日期：2026-09-25。
> 本文是《Hermes_Native_Capability_Gap_Study_Plan.md》的第一阶段执行版，不是整份总计划的启动授权。
> 范围内连续实施、不逐阶段确认；固定研究规模，不设置固定工程排障次数。

## 0. 一页合同：这轮只需要回答四个问题

1. **原生基线是否成立？** 在实际可用的 Codex 版本、模型和运行入口下，原生技能发现、显式读取、隐式选择与项目说明是否真的生效？
2. **记忆是什么状态？** 是否支持、是否开启、会话是否符合生成条件、是否已经生成并在新会话中使用？不得把这些混为一谈。
3. **真实数据能否接到运行环境？** 历史轨迹能否准确关联到对应 issue、修复前仓库、镜像与测试？有哪些无法关联或无法执行的情况？
4. **一个真实工单能否完整运行？** 从修复前 base 启动原生 Codex，正常读代码、形成补丁，并由独立检查给出可信结果。

**本轮不回答“新算法是否优于 Codex”，也不回答“是否一定需要自定义 Router”。** 没有同经验对照，就不能得出这种结论。

执行链只有：

```text
核实实际原生入口
  → 小型技能发现/使用探针
  → 抽查真实轨迹与任务关联
  → 验证两个任务环境
  → 从其他源任务制作少量原生技能样件
  → 观察原生记忆条件与生成情况
  → 两个真实任务各运行一次原生修复并验收
  → 给出进入下一阶段的条件和明确限制，停止
```

**必须交付实际探查记录，不允许只交架构图、空 manifest、CLI --help 或 CI 通过。** 但失败、未触发、记忆待生成、环境不可用都可以是有效发现；不要求全部成功才允许结束。

## 1. 与总计划的关系：只切出前置探查

总计划包含约32条经验技能、6次开发修复、48次正式比较，以及有条件的诊断分叉。本阶段不激活这些工作。[S1]

| 内容 | 本轮范围 | 后续才考虑 |
|---|---|---|
| 原生技能/记忆能力 | 核实并做小探针 | 同经验、同记忆起点的正式比较 |
| 原始数据 | 最多30个源问题的详细抽查 | 扩到200个或更多独立问题 |
| 经验技能 | 目标4条样件，不足可少 | 约32条冻结经验库 |
| 真实环境 | 2个开发任务，优先来自2个仓库 | 正式测试任务池 |
| Agent执行 | 2个任务各1次原生修复 smoke | BASE / NATIVE / ASSIST 的比较 |
| 算法 | 不训练、不修改检索排名 | 有具体证据后再决定 |

这里增加的技能样件和两次真实运行，仅用于验证数据到原生工具的可执行路径，不构成经验效果实验。第一阶段的任务、轨迹、技能和提示全部标为开发探查资产，不能在后续重新称为未见测试。

## 3. 持续授权与优先级

授权本项目内必要读取、公开数据获取、局部薄适配、隔离安装、已有额度内模型调用、两项环境验证、固定探针、必要测试、普通提交推送和本轮 Draft PR。内部阶段直接衔接，不等待用户再次确认。

遵守真实平台权限。只使用现有授权账户与设备；不购买机器/额度，不修改用户全局代理、账户、技能、记忆或权限，不自动强推、合并、ready或发布。认证必须由用户参与且现有方式不可恢复时，保存阻塞，不模拟用户操作或绕过限制。

优先级：**确认原生能力 → 确认数据与环境能用 → 实际原生执行 → 为后续比较提供条件。** 不扩建权限系统、证据平台、记忆服务、前端或分布式调度器。

固定的是问题样本、探针语义和研究执行数；安装、解析、目录挂载等工程问题不设“只许修N次”的限制。配置修复后的复测须保留旧记录和变更原因，不把多次尝试只挑最好一次。

## 4. 先完成实际环境盘点，不冻结一个猜测的版本

先运行本地只读检查，记录：

- 操作系统、CPU架构、Docker服务与镜像架构、可用磁盘/内存、已有实验环境。
- Codex可执行文件实际路径、`codex --version`、支持的CLI/App Server入口。
- 认证是否可用、可选择的执行模型和推理档位；只记录认证类型，不输出凭据。
- 实验进程里的 `HOME`、`CODEX_HOME`、工作目录、技能发现作用域和配置优先级。
- 原生技能、记忆、项目说明、子任务能力等的实际设置，以及哪些限制来自实验环境。

先用已安装、功能可用的官方客户端。必要更新只装入本轮独立环境，保留原安装。模型选择以可用性和正常任务适配为依据，不为制造困难降级执行模型，也不把开发编排模型静默当成被测模型。

一旦开始固定技能探针及真实任务，锁定客户端、模型、推理档位和主要配置。确需修配置时另记版本，不将两个版本结果拼成一次运行。

**不要求旧 `0.154.0 / gpt-5.6-sol` 必须继续使用；也不预设某个“最新模型”一定可用。** 新版本结果不得与旧分数合并称提升。

优先使用能提供所需能力的官方非交互入口或 App Server。执行前核对本机帮助/协议；不要凭旧代码臆造字段。

官方非交互模式支持 JSONL 事件记录，和“强制模型每轮生成研究JSON”不是一回事。[O3]

要求：

1. 去掉旧“最多四次工具操作后返回”“CONTINUE / TASK_COMPLETE”的人为回合协议。
2. 不向被测会话注入本Goal、历史胜负、预期使用的技能ID或研究者分析。
3. 保留目标仓库既有项目说明，不用研究提示覆盖它；实验目录不能意外继承Hermes开发目录的指令。
4. 权限允许在独立任务副本中正常读写、运行命令；真实仓库代码不在用户主目录中执行。
5. 原生执行与环境测试不获得目标参考修复、隐藏测试或未来网络答案。若限制网页检索，明确结论限于预配置的仓库维护场景，不称完整桌面产品评测。
6. 不照抄旧适配里与本轮无关的功能禁用项。确实无法保留的能力逐项说明，而非声称所有原生能力已复现。
7. 只使用公开工具事件、文件与结果，过滤私有推理内容；不逆向读取模型隐藏状态。

进程启动、事件收集、权限和统计只做薄适配。没有必要为了这两次运行建立另一个Agent框架。

## 6. 技能发现检查：不要把文件存在当作原生加载成功

当前官方文档说明了原生发现作用域与显式/隐式调用；路径可能与旧 `/workspace/skills` 挂载不同。[O1]

执行时尤其核对：**修改 `CODEX_HOME` 不自动证明 `$HOME/.agents/skills` 已隔离或指向同一位置。** 分别确认实际路径。优先把本轮技能放进实验用户技能作用域；无法使用时才用干净fixture的项目作用域，并标清这一差别。

先做无需模型生成的扫描/列表检查，若该版本提供原生列举接口则记录实际结果。没有公开列表接口时，组合可观察加载记录和后续文件读取；不能仅用LLM自述“我有这项技能”作为扫描证据。

保留：名称、description、路径、是否可发现、名称冲突、解析错误、目录截断或配置警告。完整目录可读取，但不把所有技能正文手工拼进初始提示替代渐进加载。

必要时依据官方规范修复YAML、名称冲突和description。修复以清晰表达用途为准，不把“无论任务是什么都必须调用本技能”写进描述。

## 7. 四个合成探针：只测功能接线，不测算法能力

在一次性fixture中准备3项用途不同的无害小技能，正文只做只读文件检查或在fixture内写小报告。例如CSV字段盘点、Python测试入口查找、打包说明检查。它们不是从真实任务提取的技能，也不进入后续正式经验库。

每项技能正文可包含一个无害、预先记录的报告格式标记，配合实际文件读取验证正文是否被使用。这个标记不放进隐式任务提示或description；标记出现只是接线证据，不是泛化成绩。

固定四个探针，每个独立新线程、干净fixture；隐式探针不能继承显式探针已经读过的正文：

| 探针 | 输入 | 看什么 |
|---|---|---|
| P1 显式使用 | 使用本版本支持的显式技能入口指定A | 能否加载A正文并完成无害操作 |
| P2 隐式匹配A | 描述A适用的实际小工作，不给名称/路径 | 是否自主发现/读取；没读也记录任务是否完成 |
| P3 隐式匹配B | 描述B的另一类小工作，不给名称/路径 | 是否能区分用途，不把一次成功当普遍正确 |
| P4 非匹配任务 | 一个不需要上述技能的小任务 | 是否仍不必要地加载技能；不得据一次调用断言误路由 |

每个会话默认最多180秒，时间是防失控边界，不用短截止制造失败。标准运行没有中途人为提醒“你忘记用技能”。

至少区分：`discovered`、`body_read_observed`、`action_observed`、`task_completed`、`progressive_loading_observable`。

某个隐式探针没读技能但正确完成，不标漏召回。无法看到完整初始上下文时，将渐进加载记为不可完全观察，不伪造系统提示内容。一次显式成功不代表隐式选择能力；一次隐式未触发也不能直接阻断整个数据/环境探查。

## 8. 真实数据探查：先关联，不先批量生成技能

首选数据对：[D1, D2]

```text
nebius/SWE-rebench-openhands-trajectories
       └── instance_id → 对应版本的 nebius/SWE-rebench
                          ├── repo / base_commit / problem_statement
                          ├── task patch / test_patch（可信侧）
                          ├── FAIL_TO_PASS / PASS_TO_PASS（可信侧）
                          └── 环境与镜像映射
```

两份数据各自锁定实际revision。轨迹不能默认与SWE-rebench V2通配；ID不匹配时查作者映射，不靠改字符串“凑上”。

按固定种子 `20260925` 抽取**最多30个独立源问题、每问题最多2条轨迹**。目标覆盖2–3个Python仓库；所有选样依据只使用仓库/问题身份、语言、材料可取等元数据，不根据成功率或技能正例筛选。

优先投影读取元数据列、按需读取轨迹，或者使用流式/分片访问。不能写出“先完整下载再select前30行”的代码，却报告只获取了30行的成本。确需整片下载，记录实际字节和原因，不下载模型权重或所有任务镜像。

可流式扫描更多轻量元数据来统计可关联范围；详细轨迹仍限制为已登记源样本。未完整扫描时只报告已扫描范围，不填全库独立issue数或全库join成功率。

抽样顺序、数据源偏置和仓库集中度需要说明。这30个问题是可行性抽查，不代表整个数据集。

## 9. 数据必须实际读到哪些内容

每条抽查轨迹至少核实：

```yaml
trajectory_id: actual_source_id
instance_id: actual_source_id
repo: actual_repo
trajectory_parse: OK | PARTIAL | FAILED
tool_actions_observed: true | false | null
tool_observations_observed: true | false | null
model_patch_present: true | false
author_resolved_label: original_value
exit_status: original_value
task_join: MATCHED | MISSING | AMBIGUOUS
base_commit: actual_value_or_null
image_mapping: RESOLVED | NOT_AVAILABLE | UNKNOWN
license: observed_value_or_unknown
sample_role: EXPERIENCE_SOURCE_EXPLORATION
```

要求：

- 正确解析嵌套JSON/工具参数，保留原文；不执行轨迹中的历史shell命令。
- `resolved`、退出错误、超时和测试生成字段分别保存。空值不当失败，`submit`不当成功，作者的成功标签不当本地复验。
- 同issue的多轨迹、相同补丁、成功/失败混合情况只做计数；不强行每问题选一个成功和一个失败。
- 历史动作与环境观察是主要可复用材料，不依赖或公开模型私有推理文本。
- 源历史是其他模型/OpenHands执行，不能写成“本轮Codex本人经历过这些任务”。

至少挑出3个完整的“公开问题→实际工具动作/输出→候选patch→原验证标签”链条作结构抽查。不要求它们都成功，不把失败归因写成没有证据的普遍教训。

## 10. 数据规模可行性说明：回答能否扩展，但不先扩展

给出以下实际数字，所有字段附分母/范围：

1. 扫描元数据行数、抽取轨迹行数、不同issue数、不同仓库数。
2. 在抽样中能解析的比例、能关联任务的比例、能定位镜像/安装定义的比例。
3. 同issue是否存在多个不同候选或不同结果；这些是描述性材料，不是现成的干预增益标签。
4. 已下载数据、镜像字节及实际时间；不能用轨迹压缩文件体积替代环境总成本。
5. 哪些来源信息不足以做时间划分、近重复去重或许可判断。

可引用数据卡报告的规模，但必须标“作者报告”，与本轮本地观察分栏。作者提供部分预建镜像不等于所有轨迹对应的环境都已验证。[D1, D2]

本轮不据30个样本外推“能形成数万条高质量适用性标签”。只说明可扩大读取/恢复的途径和已观察障碍。

## 11. 两个真实开发任务：在读取答案之前隔离角色

从同一来源另选最多4个环境候选，按稳定顺序优先取得2个不同仓库的任务。它们不与30个经验源问题重复；在源样件制作前完成身份和近重复检查。

这两个任务被标为 `NATIVE_RUNTIME_SMOKE_DEV`，将来不用于声称独立盲测。不得把其轨迹、model_patch或参考修复交给技能制作上下文。

选择顺序只考虑公开问题、base和环境资产。镜像确实不可恢复时可顺序使用备用候选；Agent一旦开始运行，不得因成功/失败、没有用技能或不够精彩而换题。

本轮不建立完整测试集。若无法找到2个独立仓库但有1个合法环境，可以完成较小范围，并明确不支持跨仓库可行性结论。

## 12. 先验证环境真的可执行，再启动Agent

优先采用数据作者提供的运行框架与镜像定义，复用Hermes的外层捕获/结果管理；不要为了兼容旧任务字段自行重写全部验收。

对两个候选分别验证：

1. 实际镜像引用/digest与平台；容器能启动、Python及依赖可导入。
2. 容器内目标仓库HEAD对应base；测试导入的包来自该副本，而不是宿主已安装版本。
3. 在可信验证副本中应用官方测试资产，能正确收集目标与保护用例。
4. base在至少一个指定目标行为上出现预期失败，而非缺依赖/路径错误；保护集合符合作者协议。
5. 独立参考副本应用参考patch后通过必要检查；原始计数、环境异常、skip情况保留。

参考patch和隐藏测试只在可信资格侧。Agent工作区必须重新从base生成，不能把验证时已经打过的测试或修复残留在里面。镜像若内含参考文件，也要按既有隔离方式确认它们不对被测Agent开放。

Apple Silicon上必须实测镜像架构和仿真可用性，不声称ARM原生运行。不合适时可使用用户已有、已授权的Linux资源；不新购物理资源或搭建新云平台。

原数据确实存在语义冲突或环境问题，保存资格失败。允许小型安装/路径适配，不把这一阶段变成重写测试合同；不为确保结果好看修改目标要求。

首选数据源确有接入阻塞时，可在两次真实Agent运行前明确切换到总计划中的SWE-Gym备选；单列源、revision和范围，不把两套来源拼成“原版join已成功”。若将引入大规模新适配，则先交付具体阻塞，不自动扩大工程。[S1]

## 13. 制作4条真实经验样件，不构建正式32条技能库

只用已划为经验来源的30个问题。目标4条，来自至少2个不同源问题；不足以抽出具体策略时如实少于4条，不生成泛泛的“认真检查”“运行测试”凑数。

使用统一模板和现有编排能力，最多2批来源到技能的模型转换。模型与提示记录，不训练参数。源样本的失败不自动给出因果归因；成功也不证明策略普遍适用。

每条保留：

```text
name / description
该源案例中的问题与适用前提
2–5项可执行检查或处理步骤
源案例真正使用过的验证方式
未知或不宜泛化的边界
source issue / trajectory / revision / license
```

正文目标300–600 tokens，必要引用放references；不截去条件以凑长度。不要把旧patch改写成“去特定行粘贴答案”。样件与合成探针明确区分，合成标记不得进入真实任务技能。

为样件建立原生可读的完整目录，名称/路径/description一致；部署到上一阶段已验证的发现位置。后续原生任务自由选择，不指定“正确技能”，也不保证库里一定有适用经验。

这些只是内容接入样件，不是新的蒸馏算法或已验证的技能库。

## 14. 自动记忆：观察真实条件，不要求几分钟内一定生成

先记录实际入口、开关、会话持久化方式、生成资格、空闲等待、额度条件和可观察存储。仅使用该版本公开支持的配置；文档声明不等于本地实测。

官方说明本地记忆会异步整理，可能跳过活跃或短生命周期会话，并受空闲时间与额度条件影响。因此“会话刚结束没生成”不是记忆功能失败。[O2]

本轮流程：

1. 在独立实验状态中，用最多2次正常会话阅读/讨论部分源案例和维护偏好，诚实说明材料来自历史案例。
2. 不使用会丢弃该会话持久化记录的模式来测试记忆生成；先确认所选入口是否为可用的记忆生成输入。[O2, O3]
3. 按真实生成资格等待；等待期间先完成数据/环境工作，不空转发模型请求。
4. 附加主动观察窗口最多20分钟。若实际空闲阈值更长，直接记 `PENDING_NATIVE_ELIGIBILITY` 和已知条件；不改时间戳、降低阈值或直接调用未支持的内部接口来强制造成暖启动。
5. 只有真正观察到原生生成状态时，才做1次独立新会话的使用检查。不携带原对话全文，不由宿主读出记忆正文后手工注入。
6. 使用检查应区分原生注入/检索、显式文件读取和普通推断；仅回答正确而无来源依据，不足以证明记忆已注入。

不得手写 `memories/` 内部生成文件后称为原生自动记忆。不得复制用户日常私人记忆到本实验，也不将生成的私密内容上传GitHub。

本轮记录的“2次种子会话”不替代总计划后续正式暖启动。记忆未建立不阻断技能和环境探查，也不允许写“已经测过启用完整历史记忆的最强原生配置”。

本Goal结束时不留下无限轮询/后台实验，不承诺会稍后自动报告。未成熟的记忆状态可保留在独立目录，后续阶段再显式检查；不能把等待问题变成自建记忆系统。

## 15. 两次真实原生修复：验证整条路径，而不是比较算法

在两个资格可用的开发任务上，各执行**1次**新原生Codex修复，默认900秒完整活动预算。进入前先固定任务ID、模型、配置、技能样件及提示，保存probe manifest。

配置统一为：目标仓库正常资料＋本轮同一小技能库＋完整目录。原生自行选用或拒绝，无ASSIST候选提示，无R/V关系调用，无宿主中途干预。

默认两次修复不参与生成后续记忆；已有记忆使用条件须一致并声明。如果仅有技能条件可复现，则明确采用 `NATIVE_SKILLS_ONLY`，不得暗示等同于拥有完整历史的日常产品。前述记忆探针单独运行，不让第一个目标任务的经验影响第二个。

提示只包含原始用户问题、仓库必要环境说明和相同中性提示：历史技能可作参考，不必强制使用，当前要求与实际源码优先。不指定源技能、不告诉它别的候选是否失败。

全程从同一个任务自己的修复前base新启会话。不是复用OpenHands历史对话，也不是与另一方法共享前缀的因果实验。

到正常结束或预算截止时捕获实际候选；在干净base重建，用冻结目标/保护检查验收。Agent自己运行的测试与最终可信检查分别报告。

**Agent没有修好也是一次有效smoke，只要能可信捕获和验收。** 不要求2/2通过，不因为没读技能而重跑，不把一次使用或成功说成经验收益。

## 16. 计时与事件：从最外层开始，只记录必要事实

在创建用户运行状态、准备输入和启动客户端之前开始本次在线计时。配置/权限检查发生在计时器之前还是之内要明确，不能重演“做完checkpoint验证才计时”的漏项。[S2]

分别记录：一次性数据/镜像/技能准备、记忆准备、技能探针、真实修复、最终验收。真实修复至少包含本次在线准备、客户端初始化、服务等待、工具活动、最后输出与清理。

已有镜像就绪场景可以声明；不把下载全部镜像时间计入Agent单题，也不能说已经测试冷启动。停止时保留超时与现有补丁，超时不是自动功能FAIL。

公开事件至少支持复核：工作目录、模型、是否新线程、工具命令及有限输出、技能正文读取、文件变动、终态、总token与实际用时。缓存token是子集，不重复相加。不可观察字段留空并说明，金额无账单则不填。

若存在完整计时缺口，保留功能结果并单列成本未知；不重跑测一个新值来填旧账。这里不增加复杂成本预测器。

## 17. 三种容易误判的结果

| 观察 | 可以说 | 不能说 |
|---|---|---|
| 正确完成，但未读技能 | 原生在本例可能不需要该资料 | 技能召回失败 |
| 显式可读、隐式未触发 | 功能接线部分成立，隐式选择本次未观察到 | 原生路由算法有缺陷 |
| 读了技能且修复通过 | 有可见使用和功能结果 | 技能导致成功或Hermes优于原生 |
| 技能正文与目标条件不兼容 | 有值得人工理解的候选内容/迁移问题 | 新适用性网络一定能解决 |
| 记忆开关开启但尚未生成 | 配置已开启，暖记忆未建立或待资格 | 已测试完整记忆能力或原生不会记忆 |
| 镜像无法运行 | 数据/平台接入受限 | Agent能力不够 |
| 作者标签成功，但本地复验不一致 | 记录版本/环境/验证差异，待解释 | 直接改源标签或只保留成功任务 |

第一阶段最多给出待验证的发现/适用性/内容/执行/成本假设，`algorithm_gap_evidence`必须保留 `NOT_ESTABLISHED`。

## 18. 研究规模与不自动扩张

| 工作 | 本轮基准规模 | 说明 |
|---|---:|---|
| 元数据扫描 | 按需轻量读取，范围实报 | 不等于读取全部轨迹 |
| 源问题详细抽查 | ≤30个问题、每问题≤2轨迹 | 不据结果挑正反例 |
| 合成技能探针 | 4个会话 | 非真实任务，不作效果指标 |
| 真实技能样件 | 目标4条，最多2批转换 | 不构建32条正式技能库 |
| 原生记忆 | ≤2个种子会话＋条件满足时1个使用会话 | 原生后台生成调用另外计量 |
| 环境资格 | 目标2个、有限候选≤4 | 基于资源资格，不基于Agent成败 |
| 真实修复 | 2任务×1次＝2次 | 无BASE/NATIVE/ASSIST比较矩阵 |
| 新训练/关系矩阵/诊断分叉 | 0 | 本阶段明确不做 |

最完整的计划是4次技能探针、至多2批技能转换、至多3次记忆相关会话、2次真实修复。它们用途不同，不能统称11个真实修复任务；自动记忆子调用、工程复测、资格测试和验收另记。

探针默认每次180秒；技能转换/记忆种子会话默认每次至多300秒；真实修复每次900秒。因实际服务无法在此时间内正常工作，需要调整时应在对应探针首次执行前说明并锁定，不靠缩短预算制造失败。

工程修复后的复测可继续，但必须针对明确变化，保存此前结果；不能反复重抽同一隐式任务直到触发，再只报成功。真实修复一旦开始不得增加新样本覆盖失败；可以恢复原会话及剩余预算，无法恢复则保留UNKNOWN。

资源不足时缩小未开始部分并说明，不切换新付费服务、不偷偷降低模型能力、不替换成模拟执行充数。

## 21. 退出决策：只决定下一步可以测什么

| 条件 | 结论 |
|---|---|
| 原生技能路径成立、数据可关联、两任务能产生可信补丁结果 | `READY_FOR_SMALL_SAME_LIBRARY_PILOT`；可以规划下一阶段，不自动开始 |
| 上述成立，但记忆未成熟/不可用 | `READY_SKILLS_ONLY_WITH_MEMORY_LIMITATION`；不称完整暖记忆基线 |
| 只有一个仓库或一个可信环境 | `LIMITED_SCOPE_READY`；写明范围，不推断跨仓库 |
| 文件可读但原生发现/调用尚未确认 | `NATIVE_CONFIGURATION_BLOCKED`；优先修接线，尚不训练路由器 |
| 轨迹多但任务/镜像关联不足 | `DATA_ENVIRONMENT_BLOCKED`；说明具体缺口和备选，不声称大量可执行数据就绪 |
| 有运行记录但候选/验收不可信 | `PARTIAL_EXECUTION_EVIDENCE`；不能以模型自评代替 |

隐式未触发本身不等于配置阻塞：若扫描/显式调用已证实，只记一次行为未观察；不要要求所有探针都用技能。

阶段完成与后续就绪分开。充分记录一个真实阻塞，可以完成探查报告，但不能标平台就绪。所有真实工作尚未执行，仅给计划或测试桩时，必须标 `PARTIAL_IMPLEMENTATION`。
