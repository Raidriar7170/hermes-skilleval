## 0. 目标与完成体验

本轮应交付一条能实际运行的路径：

```text
公开请求＋固定版本源码＋技能包
    → 按位置区分普通正文与代码区域
    → 只纠正有证据的正文误判，保留真实／歧义代码引用
    → 在隔离目标环境中探测明确的必要条件
    → 分别给出文本输入、支持资格、执行环境的就绪状态
    → 先运行无模型预检
    → 条件具备时运行冻结 A 模型的有限评分与后验校准
    → 返回对应范围的建议／拒绝，不认证未验证的修复效果
```

必须交付代码、真实环境探测记录、反例测试、安装入口和 GitHub 可读结果。仅增加字段、把环境设成 true、或再次输出没有尝试探测的 UNKNOWN，不构成本轮实质完成。

没有有效阈值仍可以如实结束，但要区分：解析修复、环境探测、预检可行性、后验操作点、独立效用。不得用一个 COMPLETE 代替这些不同判断。

## 5. M1：按 span 修复，而不是按名称全局替换

推荐处理次序：

1. 在原始 request 上定位受保护的代码／歧义区域，保留字符偏移。
2. 仅在确认属于普通正文的区域中定位可纠正的括号补充语。
3. 将可纠正对象保存为具体 span，而不是可被任意替换的单词集合。
4. 对每个底层 `explicit_call_unlocated`，检查其所有同名调用形态出现位置。
5. 只有这些出现位置全部属于已确认的正文补充语，才移除该条误判。
6. 任一出现位置位于代码区域、跨区域边界、未闭合／解析不确定区域或歧义调用中，继续保留原 missing。

只改变“这一条缺失是否为解析误报”，不修改给模型看的原始请求，不移除代码，不新增请求中没有的函数、义务或事实。

代码区域识别至少处理：单／多反引号行内代码、反引号／波浪线围栏代码块、缩进代码块；匹配与边界可参考 CommonMark 的对应规范。[E1]

可以复用已存在的轻量解析库；没有合适能力时使用小型位置扫描器。不要用渲染后的文本重新搜索原字符串来猜偏移。库无法提供准确映射的复杂嵌套、未闭合输入等，可以保守不纠正，明确这比标准 Markdown 更保守，不声称完整符合所有语法。

**不要再次在完整 request 上使用按名称的 `re.sub` 来判断“是否还剩真实调用”。**

## 6. 解析修复的最小测试面

测试按行为覆盖，不以测试数量为目标：

| 情形 | 应有结果 |
|---|---|
| 仅普通补充语 `warning (maybe allowing…)` | 允许纠正这一条误报 |
| 仅代码 `warning (maybe + value)` | 不作为正文纠正 |
| 同名正文＋反引号代码 | 保留代码对应的关键缺失 |
| 同名正文＋围栏／缩进代码 | 同上 |
| 普通正文＋相邻调用 `warning(value)` | 保留真实调用检查 |
| 普通正文＋歧义空格调用 `warning (value)` | 不强行解释为正文 |
| 同一名称出现多次、顺序交换 | 任何受保护出现都不能被另一处抵消 |
| 不同长度反引号、波浪线围栏、CRLF、中文前缀 | span 不偏移、不跨区域删除 |
| 语法不确定或超出解析范围 | 不自动移除关键 missing，明确原因 |
| 真实文件缺失、预算不足、越界、符号链接 | 继续执行已有拒绝规则 |

再运行四条真实旧 cal 请求，核对合法正文误报仍被纠正，源码、预算和其他缺失保持原义。

改变提取语义后新增版本身份。旧记录继续引用旧实现／原上下文，不刷新旧摘要让它看似从未存在问题。

## 7. M2：先定义环境问题，再执行探测

不要继续把环境当成没有解释的 `environment_known`。

用一份短、可读的要求清单回答：

- 针对哪个仓库、哪份源码版本、哪种使用方式？
- 需要什么 Python、包、CLI、输入文件、SQLite 特性或网络条件？
- 这一要求来自技能正文、项目配置、公开请求，还是本轮事先固定的工程约束？
- 什么观测足以确认它？什么情况是明确不满足？什么情况只是没有测到？

本轮使用方式固定为**隔离源码维护／技能建议**，不扩展为对远程业务系统执行命令。

某技能仅作为开发指导被阅读，不代表必须执行它正文中的全部示例命令；反之，计划实际调用某个工具，就必须确认该工具及其必要前提。该差别必须在探测前写入 scope，不能看到某项缺依赖后才宣布“不需要”。

未知依赖、未声明版本或歧义要求不能凭模型猜测填真。确实不属于当前 scope 的条目可标 `NOT_REQUIRED_FOR_SCOPE`，附理由；它不是“已安装”或“已满足”。

## 8. 分层结果：不再用一个布尔值代表全部资格

复用现有建议／支持／执行的分层，新增结构化事实，不另建平台：

| 层次 | 要回答的问题 | 不能由它推出的结论 |
|---|---|---|
| 文本输入就绪 | 版本、请求、相关片段、技能证据与 token 是否可用 | 工具已安装、问题必能修复 |
| 技能条件事实 | 此任务使用该技能的明确前提是否得到证实 | 模型达到文本精度或预测成功率 |
| 目标环境就绪 | 选定源码可在指定环境导入、基本入口可运行 | 目标故障已修复或完整回归全绿 |
| 支持操作点 | 指定模型／输入／规则是否具有合格后验阈值 | 新任务泛化、执行许可、安全保证 |
| 修复验收 | 实际候选补丁是否通过对应检查 | 本轮不执行此层，保持 NOT_RUN |

对单项事实使用 `SATISFIED / UNSATISFIED / UNKNOWN`；对整组必要条件计算摘要，不由调用者直接指定摘要。

缺少必需命令是 UNSATISFIED；下载失败、探针超时或证据不足通常是 UNKNOWN，必须说明原因。未运行不能写成失败，也不能写成通过。

旧严格协议仍保留。新有证据路径对同一 scope 的必需条件不能更宽松，只是让这些条件变成可验证项。**本轮不启用新的“text-only 校准免环境要求”协议来绕开旧阻塞。**普通 advisory 继续按原允许范围工作，并保留限制说明。

## 9. 事实记录与身份：足够使用，不建设证明系统

建议一份任务环境记录包含以下字段，命名可以按已有结构调整：

```json
{
  "schema": "environment-readiness-v1",
  "task_id": "ACTUAL_TASK",
  "repository": "ACTUAL_OWNER/REPO",
  "source_revision": "EXACT_REVISION",
  "snapshot_identity": "ACTUAL_IDENTITY",
  "scope": "isolated-source-maintenance",
  "profile_version": "ACTUAL_PROFILE",
  "observed_at": "ACTUAL_TIMESTAMP",
  "runner_identity": "ACTUAL_RUNTIME_IDENTITY",
  "requirements": [],
  "observations": [],
  "required_conditions_state": "UNKNOWN",
  "execution_authority": "NONE"
}
```

上面是字段示例，不是实际测量结果；占位符配置不能作为有效证据运行。

每项 observation 至少有探针 ID、受控参数、退出状态、结构化结论、必要的截断输出和耗时。记录来源版本、解释器／镜像、依赖清单指纹、探针版本与要求 scope；私密绝对路径只保留在本地。

文件摘要只用于一致性与防止误混，不证明文本内容为真。不得接受一个只有 `{"task": true}` 的文件作为新的已验证事实。

已有 `--environment-known` 或旧布尔映射可以保留历史兼容，但新 `verified` 路径不得据此直接通过。要重新从匹配当前环境的探针结果推导。有人声明已知，只能标为声明，不能标为已测。

环境改变、依赖重装、源版本或检查 scope 改变后，相关观测失效；相同不可变镜像／依赖与源码条件可按规则复用，不能只因路径名字相同就复用。再次实际使用前完成轻量核对；无从确认时重新探测。

## 10. M3：真实探测四条已有校准任务

使用当前冻结来源中的四条任务，不新建任务，不移入 check 来凑数：

```text
sqlite-utils-issue-211
sqlite-utils-issue-236
csvkit-issue-1148
csv-diff-issue-31
```

先核实 ID、来源 revision、原始源码快照、依赖配置与分区。缺失旧快照时可按记录的公开 revision 重建并核对；不能拿当前最新版源码冒充旧任务。

不同任务即使来自同一仓库，也可能依赖不同版本；允许共享已证明一致的镜像层／安装资产，但事实须绑定各自快照。

建议每个环境至少覆盖：

1. 解释器、平台与固定环境配置。
2. 源码安装／导入状态；确认 `__file__`、模块 origin 或等价定位确实指向该源码，而不是系统最新版。
3. 项目要求的依赖完整性；可使用 `python -m pip check` 作辅助，但它只检查已安装分发包的依赖相容性，不单独证明目标项目已安装或可执行。[E2]
4. 该版本的必要 CLI 或库入口，使用无副作用的 help／最小接口探针。
5. 对当前声明用法确实必需的特性，例如在临时数据库确认某项 SQLite 能力。只探测来源中要求的特性，不假定所有技能都需要 FTS 等可选能力。
6. 隔离网络与工作目录写入范围，与本轮使用 scope 一致。

探针不是目标修复测试。存在已知 bug 的 base 不必先通过那条故障测试才能有环境资格；但缺依赖、错误导入或入口不可运行不能用“这是 bug 本来就会失败”掩盖。

## 11. 环境准备的安全与实用边界

优先复用 `_maintenance` 已有 profile、容器和独立工作目录。不把 Docker socket、用户主目录、GitHub／模型服务凭据或其他任务目录挂进目标环境。

安装和 import 可能执行第三方代码，所以目标仓库的构建、CLI与探针必须在隔离环境中运行，不在用户主 Python 环境直接执行。运行参数来自经检查的程序配置，不能把 issue／SKILL.md 的 shell 文本原样当命令运行。

使用参数数组与明确超时／输出上限；不使用无边界 `shell=True`、任意插件或递归执行。需要修改安装依赖配方时只改本轮环境配置，不修改旧任务源码来让安装通过。

现有资源不足时允许取得公开必要依赖、构建本轮专用镜像。不得升级账户权限、变更全局设置或新增付费资源。连续失败应定位版本、架构、离线缓存或网络原因，不无限猜版本。

必须实际尝试合法可行的准备方式，再判资源阻塞。只有写好探针代码、没有在四条环境中尝试运行，不能称真实环境事实已建立。

## 12. M4：接入同一份资格判定

新增少量 helper／配置并接入已有 `hermes-applicability`，不要另造独立服务。

建议职责如下（命令名为新增设计，开发者需以实际 CLI 校验）：

```text
probe-environment   获取并保存实际环境事实；不构造模型
preflight           使用环境事实、修复上下文和 token 信息，返回分层资格
aligned-score       按冻结 A/J 目标，在对应操作的预检后评分
aligned-calibrate   仅对匹配的 cal 数据与模型拟合校准
advise              返回用途明确的建议；严格支持需要有效绑定
```

环境事实解析、必需条件归约和资格判定必须在 preflight／score／calibrate／运行时共用。不要让离线检查认为环境就绪，实际评分却仍被另一个默认 False 阻断；也不要在一处只检查状态字符串、另一处检查真实条件。

按操作目的检查：

- 存档 records 重算不要求目标环境在线，也不声称当前环境已就绪。
- advisory 检查它实际需要的输入，不因尚无支持阈值就拒绝所有建议。
- strict cal-score 先做无模型的必要条件检查，随后才取得本地 tokenizer／模型。
- 支持评分没有合格阈值时不得设置 accepted=true，也不得偷偷当作固定 Top-2。
- 本轮任何操作都不获得修复 Agent 启动许可。

## 13. 输入、模型与事实绑定不能脱节

修复上下文标记或正文过滤后，必须使用新输入身份。即使只是摘要中 `partial → usable`，也可能改变实际模型输入。

- 保存原始 request，不让 span 修复改变用户原文。
- 预检后直接使用同一份已准备公共输入对象评分，或严格验证再次提取的内容相同；不要因计时／扫描顺序波动默默换输入。
- 新 token 记录绑定新公共输入与当前 tokenizer；未知完整性不能当作完整。
- 不把旧 logits 配上新资格状态冒充新推理；新输入必要时真实重评分。
- 模型参数不变，但输入／资格／scope 变化会使旧 calibrator 不可直接复用。
- 支持对象包含模型、A/J目标、输入版本、环境要求版本和阈值来源，运行前检查匹配。

保持旧 Gate 与原 rank 冻结。任何新支持版本不得仅改 hash 就借用旧 Gate 反馈。

## 14. 条件成立时：完成一次有限的 A 评分与后验校准

本轮不应在环境明明已准备好时，仅交付一张“预检通过”表就结束。

若四条原 cal 中满足原规则的必要条件、A checkpoint与本地推理资源可用，则继续运行：

```text
新上下文与环境事实冻结
    → A：原有适用性候选，单轴真实评分
    → 原规则的适用性校准与精度—覆盖曲线
    → 独立进程重载校准JSON并重算
    → 输出后验阈值或仍无阈值
```

只使用已冻结 A 候选，不搜索模型、不重训、不因 J 分数更好替换 A。建议评分范围就是四条 cal × 现有十个技能，不扩展至新的 check／全历史任务。

保留原操作点规则：精度目标、至少三组、至少六个已知接受行、覆盖要求和 UNKNOWN 处理均以当前冻结文件为准；开始时打印读取值。不能通过降低门槛、删除不合格任务或重复一个组获得阈值。

所有任务／候选保留在适用分母，资格不足的行不作为合格接受项。报告各阶段分母与原因，不将未知项填负。

J 保持明确的原始建议分数；现有条件特异性 cal 正例不足不能升级成已校准，也不应阻断只需适用性轴的 A。

若输入变化使原弱标签依据发生实质改变，标注需重新审核，本轮不新增标注来修表；受影响的统计保留限制，不冒充完整原目标评估。

## 15. 后验阈值不等于已建立独立操作点

这四条 cal 及旧 check 已经被多轮观察。获得新阈值时只能标 `RETROSPECTIVE_ONLY`，不得宣称90%真实精度、安全保证、跨仓库泛化或修复率提升。

本轮不再读取旧 check 选择新阈值；不据失败结果增加新组或新规则。没有合格阈值则仍为 `NOT_ESTABLISHED`，不重复一套回退 Agent smoke。

保留完整阈值曲线与预定选点结果。Brier／log-loss、排序、接受精度与环境资格分别报告；旧 check 自身正例率只能叫事后常量参考，不当成部署基线。

数值拟合和重载是软件验证，不是独立泛化验证。最多在同一匹配 cal 输入上验证校准后决策的一致性，不能将 calibration 对象的已登记输入范围扩大成任意新任务。

## 16. 真实安装入口验证，而不是只测试拒绝分支

建立干净的轻量 wheel 环境，在 checkout 外验证：

- help、旧 records、新 span 检查与环境事实读取可以运行；轻量分支不加载 Torch／Transformers／PEFT。
- 缺少事实、错配源码或失败探针能够在模型构造前明确拒绝。
- 至少一个环境事实文件来自真实目标容器，而不是测试中写出的 true。
- 若真实环境已就绪，已安装 CLI 能把该事实一路传到 preflight／score，不因参数遗漏重新变成未知。
- 条件式 A 评分实际执行时，选定一个事先按固定顺序确定的 cal 行，从已安装入口复现相同模型输入与输出；该行无需被阈值接受。

安装环境不带数据集和权重时，使用明确的外部路径参数，不依赖个人主目录。公开 usage 的命令必须实际验证；计划中的参数不能当作已有命令交付。

若所有真实目标环境均无法建立，保留探针结果和安装拒绝验证；`environment_validation` 不可标 COMPLETE。不能再用假环境的一次通过替代真实条件。

## 17. 环境事实与集成回归

除第6节解析测试，至少覆盖以下行为：

| 反例／场景 | 必须保持的结果 |
|---|---|
| 没有facts文件或仅手写 true | 新 verified 路径不据此认证环境 |
| `pip check` 通过但目标包未安装 | 目标环境仍未确认 |
| import到了系统最新版 | 拒绝绑定旧任务源码 |
| 工具存在但必要版本／能力不满足 | 对应条件不满足，不扩大为模型失败 |
| 探针超时或依赖下载失败 | 保留具体 UNKNOWN，不填PASS |
| 核心前提未知、可选工具未安装 | 两者分开；不因可选项误阻断，也不忽略核心项 |
| 只确认联网能力却要求离线 | 不推导“离线限制已生效” |
| 换source revision／依赖profile／snapshot | 原facts不被错误复用 |
| 预检至使用期间事实条件变化 | 检查失效，重探测或拒绝 |
| 环境就绪、支持阈值为空 | 仍未建立支持，advisory与strict分开 |
| 只有两个合格机制组 | 仍在零model forward下拒绝严格校准 |
| A调用 | 不读取特异性输出，不因该轴标签不足被错误阻断 |
| 新输入＋旧logits／calibrator | 身份不匹配，不能偷换 |
| 旧记录重算 | 原语义、状态与数值不变 |

构造测试、真实环境探针、tokenizer-only、模型 forward、校准拟合分别记录。探针程序成功退出不自动等于被探测条件满足。
