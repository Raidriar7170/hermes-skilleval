# 双仓库维护复盘（一页）

本轮交付的是两个已验证配置共用的历史维护回放组件。主研究为六个新修复族、每族 N/F/S 各一次；开发题另外报告。结果以[逐题表](results.md)为准。`assist` 未实现，无外部用户采用、上游合并或生产效果证据。

## F 是否足够？

固定组合为 `cli-api-regression` + `systematic-debugging`，在确认前冻结，对同仓库所有请求不变。它已经能完成多个实际修复，但 rowid 家族的有效失败说明“有通用技能”并不保证覆盖所有边界。csvkit #1247 的主结果受未告知的 fixture 路径限制影响，不能据此说 F 不会修。统一事后审计中原 N/F 补丁均通过，但这不是一次新的有效主比较。

因此当前不应因项目名称而默认开启强检索；原生或固定流程可以作为更简单的使用起点。小样本既没有证明 F 足够处理任意维护任务，也没有证明 S 带来净收益。

## S 为何换包？

S 使用真实 SkillRouter encoder/reranker 对公共请求与五个通用技能打分，选择 Top-2；[选择与读取表](results.md#selection-exposure-and-observed-reads)直接链接每题分数、包标识和事件。前五个确认族都选中 schema-change-regression + cli-api-regression，第六个 FTS 族改选 schema-change-regression + verification-before-completion；这六组集合均不同于 F。变化来自冻结打分路径，没有利用答案或运行结果调参。FTS 的 S 虽通过，但没有被提取器观察到成功的技能读取命令。分数解释的是选择机制，不能解释某个补丁一定由某技能造成。

挂载、命令中引用、成功的读取命令、最终修复通过是不同证据。仅有路径引用或 Agent 自述不算成功使用；即使看到读包与通过同时发生，单次试验仍不能证明因果。S 的推荐耗时真实存在，Agent tokens 的随机差异与缓存比例又会影响总体成本，因此不能只看检索快慢或单次 token 数宣布节省。

## 第二仓库到底改变了什么？

适配新增了 csvkit 的包/CLI 来源检查、受控依赖安装、可写路径、可信目标与相关回归选择。较旧的 csvkit CLI 使用 `.run`，开发时按对应 base API 修正，未把新版使用方式强加给历史任务。共同执行器仍负责隔离副本、技能呈现、真实文件差分、干净 base 重建、可信测试启动和结果导出；没有为 csvkit 复制另一套主流程。

隔离 wheel 安装和 N/F 无模型依赖已经验证；当前只承诺这两个配置。确认时暴露的 `examples/` 路径限制信息缺陷，在后续交付 prompt 中修复为明确列出可写根。所有确认仍绑定原冻结源码，不能把新提示说成已在这批 Agent 运行中验证。

## 一份补丁为什么通过？

[csvkit #1219 F 补丁详解](patch-walkthrough.md)：`field_size_limit` 应设置在 csv 模块的全局解析限制，不能作为无效关键字传给 DictReader。候选补丁在独立 base 上重建后，两个指定目标与两个相关回归均通过；base 的同目标先失败、参考修复先通过。这个链条支持该限定行为的修复，不覆盖未运行的 csvpy 接口或全部上游测试。
